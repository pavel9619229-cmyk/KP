📦 KP Processing / 1C Integration

Архитектурная диаграмма обработки КП из 1С

Полная схема текущего проекта: ручной refresh, вычисление статуса КП на сервере, клиентский UI, локальный runtime cache и публикация данных через GitHub + Render.

Основной поток Browser → Render API → 1C OData → Cache → UI
Ключевой файл api_proxy.py
Фронт dashboard.js / app.js
⚙️ Что делает система

Забирает КП из 1С, строит локальный runtime snapshot, вычисляет статус по правилам и отдаёт уже готовые строки в UI.

Ручной refresh синхронизирует данные, а UI показывает таблицу, фильтры и состояние обновления.

LLM здесь не нужен — основной режим работает по серверной логике и правилам статусов.

📊 Архитектурная диаграмма

Главный поток обработки КП из 1С

Основной поток: пользователь запускает refresh → фронт вызывает Render API → backend тянет КП из 1С → вычисляет статус → сохраняет runtime snapshot → UI показывает уже готовые данные.
Где ломается дата snapshot: в точке СБОЙ ДО WRITE SNAPSHOT (красный блок у шага write snapshot): если процесс перезапускается/обрывается до этой записи, остается предыдущий snapshot и старая дата.

🔧 Компоненты системы

Что за что отвечает
dashboard.js
Фронт обработки КП
  • Загрузка таблицы через /api/kp/all
  • Ручной refresh через /api/kp/refresh
  • Показывает статус выполнения и ошибки
api_proxy.py
Центральный backend
  • Тянет КП из 1С OData
  • Собирает runtime cache и meta
  • Отдаёт /healthz, /api/kp/all, /api/kp/refresh/status
status_rules.json
Правила вычисления статуса
  • Определяет статусы по флагам КП
  • Используется сервером для statusKpComputed
  • Позволяет менять логику без переписывания фронта
data/runtime_versions
История снапшотов
  • Хранит confirmed runtime snapshot
  • Используется после refresh и при восстановлении
  • Даёт откат к стабильной версии

🧭 Источники данных

Откуда берутся данные
1C OData
Основной live-источник
  • Документы КП, статусы, суммы, даты, признаки
  • Пакетная загрузка stage1 → stage6
  • Обновляется по ручному refresh
GitHub main
Источник деплоя и confirmed версии
  • Render отслеживает ветку main
  • После refresh публикуется versioned runtime snapshot
  • Используется как опора для восстановления
Local runtime cache
Быстрая отдача UI
  • data/kp_runtime_current.json
  • data/kp_runtime_meta.json
  • Используется при старте и для health/status

🔄 Поток обработки КП

Что происходит при ручном refresh
1
Пользователь нажимает «Обновить»
Фронт стартует /api/kp/refresh и начинает опрос статуса.
2
Backend читает 1С
`fetch_rows_from_odata()` собирает КП, комментарии, оплаты и флаги стадий.
3
Считается статус
Сервер применяет `status_rules.json` и формирует `statusKpComputed`.
4
Сохраняется runtime snapshot
Данные попадают в локальный cache и подтверждённую версию для UI.

🗣️ Примеры и режимы

Что показывает и как работает система

  • Использует серверные флаги
  • Не зависит от LLM
