Блок-схема: путь данных из 1С в UI

Где именно в backend может произойти затирание актуального snapshot

Основной поток данных
Слой кэшей и публикации snapshot
Действия пользователя и обратная запись

1) 1С OData

Документы КП, реквизиты, комментарии, статусы.

2) Backend fetch

Чтение данных из 1С и сбор сырых строк.

3) Нормализация

Правила статусов, enrichment, подготовка полей.

4) Runtime consistency

Выбор authoritative snapshot между local и GitHub.

Источник затирания: здесь может быть перезапись _cached_rows старым snapshot.

5) Оперативный кэш

Актуальный набор в памяти процесса: _cached_rows.

6) Runtime-файлы

data/kp_runtime_cache.json + meta + current.

LOCAL (сервер)

Локальная файловая система Render: директория data/* и runtime-файлы.

7) Версии snapshot

data/runtime_versions/* + pointer текущей версии.

8) GitHub publish

Публикация snapshot и current-pointer в репозиторий.

9) API + UI

/api/kp/all и /ws/kp → отрисовка карточек на dashboard.

10) Действие в UI

Кнопка запускает endpoint, backend делает PATCH в 1С и цикл повторяется.

LOCAL находится в блоке "LOCAL (сервер)": это локальная файловая система сервера (папка data/*). Важно: API/UI получает данные не только из ветки GitHub, но и напрямую из local-кэша (_cached_rows). Поэтому затирание возможно до этапа 8, если runtime consistency выбрал старый authoritative snapshot и перезаписал local-кэш.
