Процессы, использующие snapshot

  1. Runtime consistency sync: выбор authoritative snapshot local/GitHub и выравнивание _cached_rows.
  2. Manual refresh: полный цикл загрузки и обновления runtime snapshot.
  3. Publish confirmed snapshot: запись версии в GitHub и продвижение current-pointer.
  4. Refresh cached rows only: частичный refresh с опорой на текущий snapshot в памяти.
  5. Payments-only refresh: обновление оплат с применением к текущему snapshot.
  6. API /api/kp/all: перед выдачей данных выполняет sync confirmed snapshot.
  7. WebSocket /ws/kp: перед пушем обновлений выполняет sync confirmed snapshot.
  8. 1/4 (/api/kp/refresh/stage1_4): stage1_base → stage2.5 → stage2 → stage3 → stage4 → stage5 (карточка КП: комментарий, клиент, менеджер, товар/цена) БЕЗ stage6 (include_stage6=False) — заказы/накладные/оплаты в этом шаге не пересчитываются.
  9. Оплаты / payments-only (/api/kp/refresh/payments-only): stage6-скан заказов+платежей поверх текущего snapshot, только paymentReceived/invoiceCreated.
  10. 4/4 (/api/kp/refresh/stage4_4): поиск приходов оплаты — Document_ПоступлениеБезналичныхДенежныхСредств. Обёртка над payments-only механизмом: скан заказов (Document_ЗаказКлиента) выполняется обязательно — без него не из чего брать номера заказов для сопоставления с назначением платежа; скан накладных (Document_РеализацияТоваровУслуг) пропущен намеренно (skip_invoice_scan), т.к. он влияет только на invoiceCreated и не нужен для статуса «Оплата получена»/блока 3. Внутри одного запуска используется один источник результата (текущий проход stage6), без повторного пересканирования тех же данных вторым шагом. После завершения — публикация найденных изменений в GitHub и UI.
  11. Просмотр Блок 1/2/3 (/api/admin/payment-match-table): при каждом открытии страницы блока выполняет тот же live-скан заказов+платежей и теперь дополнительно сохраняет найденные совпадения (paymentReceived, только повышение False→True) в runtime snapshot — без отдельного нажатия кнопок «Оплаты»/«4/4».
  12. Background refresh loop: регулярный фоновый пересчёт runtime состояния — выключен по умолчанию (ENABLE_BACKGROUND_REFRESH=false).

Сейчас дополнительно весь сервис временно suspended в Render, поэтому все runtime-процессы остановлены до ручного Resume.

От чего зависит длительность полного refresh

  1. Глубина цикла: полный проход дольше, checkpoint-восстановление быстрее.
  2. Скорость 1С OData: чем медленнее ответы, тем дольше общий цикл.
  3. Объем данных (число КП/строк): больше строк = больше запросов и проверок.
  4. Ретраи и таймауты на этапах enrichment (особенно stage2.5/3/4).
  5. Скорость publish в GitHub и подтверждения current-pointer.
  6. Конкуренция за lock: запуск может ждать завершения уже идущего refresh.
  7. Практический диапазон: от десятков секунд до нескольких минут; hard ceiling для manual refresh около 21 минуты.

Что делает каждый stage (fetch_rows_from_odata)

  1. stage1_base: backward-скан Document_КоммерческоеПредложениеКлиенту за целевой диапазон дат — получает Ref_Key, Number, Дату, Статус для каждого КП.
  2. stage2.5: параллельный fetch полного документа по каждому Ref_Key — получает Комментарий, строки Товары/услуги, navigation-links на клиента/менеджера.
  3. stage2: парсинг поля Комментарий → флаги (КП отправлено, клиент увидел, ЭДО отправлено, отказ, проблема, отгрузить, оплата пришла по тексту комментария).
  4. stage3: резолв имени клиента по navigation-link из документа.
  5. stage4: резолв имени и «заполненности» менеджера по navigation-link из документа.
  6. stage5: проверка наличия товара и заполненности цены по первой строке документа.
  7. stage6: тяжелый enrichment — скан Document_ЗаказКлиента (заказы), Document_РеализацияТоваровУслуг (накладные, влияет только на invoiceCreated) и Document_ПоступлениеБезналичныхДенежныхСредств (оплаты) — сопоставление КП → заказ → оплата, результат идёт в поля invoiceCreated и paymentReceived («Оплата получена», блок 3).
