Процессы, использующие snapshot

  1. Runtime consistency sync: выбор authoritative snapshot local/GitHub и выравнивание _cached_rows.
  2. Manual refresh: полный цикл загрузки и обновления runtime snapshot.
  3. Publish confirmed snapshot: запись версии в GitHub и продвижение current-pointer.
  4. Background refresh loop: регулярный фоновый пересчет/обновление runtime состояния.
  5. Refresh cached rows only: частичный refresh с опорой на текущий snapshot в памяти.
  6. Payments-only refresh: обновление оплат с применением к текущему snapshot.
  7. API /api/kp/all: перед выдачей данных выполняет sync confirmed snapshot.
  8. WebSocket /ws/kp: перед пушем обновлений выполняет sync confirmed snapshot.
  9. ПРОЕКТ (обсуждается, не реализовано) 1/4: базовый скан КП + карточка документа (товары/услуги, комментарий, клиент, менеджер, цена товара) — объединяет нынешние stage1_base + stage2.5 + stage2 + stage3 + stage4 + stage5 в один проход:
    1. Скан Document_КоммерческоеПредложениеКлиенту (backward pagination, как сейчас stage1_base) — получает актуальный список Ref_Key в целевом диапазоне дат.
    2. Сравнение полученных Ref_Key с текущим snapshot — любой новый Ref_Key считается новым КП (без доп. запроса к 1С).
    3. Для каждого КП (нового и уже известного) — fetch полного документа по Ref_Key (как сейчас stage2.5) — параллельно, получает строки Товары/услуги, поле Комментарий и navigation-links на клиента/менеджера.
    4. Парсинг поля Комментарий → флаги (как сейчас stage2).
    5. Резолв имени клиента по navigation-link — доп. HTTP-запрос на КП (как сейчас stage3).
    6. Резолв имени и «заполненности» менеджера по navigation-link — доп. HTTP-запрос на КП (как сейчас stage4).
    7. Проверка наличия товара и заполненности цены по первой строке (как сейчас stage5) — берётся из уже выгруженного документа, доп. запрос нужен только в редком fallback-случае, когда Товары отдаётся как nav-link без inline-данных.
    8. Публикация результата шага — commit в GitHub + обновление runtime snapshot / UI — до того, как запустятся шаги 2/4-4/4.
    Что НЕ попадает в 1/4: stage6 (заказы/накладные/оплаты, включая статус «Оплата получена») — он остаётся в шагах 2/4-4/4 и не вычисляется в этом проходе.
  10. ПРОЕКТ 2/4: скан появления новых созданных заказов (счетов) — Document_ЗаказКлиента; после завершения — публикация найденных изменений в GitHub и UI.
  11. ПРОЕКТ 3/4: скан появления новых созданных накладных — Document_РеализацияТоваровУслуг; после завершения — публикация найденных изменений в GitHub и UI.
  12. ПРОЕКТ 4/4 (реализовано, /api/kp/refresh/stage4_4): поиск приходов оплаты — Document_ПоступлениеБезналичныхДенежныхСредств. Обёртка над существующим payments-only механизмом: скан заказов (Document_ЗаказКлиента) выполняется обязательно — без него не из чего брать номера заказов для сопоставления с назначением платежа; скан накладных (Document_РеализацияТоваровУслуг) пропущен намеренно (skip_invoice_scan), т.к. он влияет только на invoiceCreated и не нужен для статуса «Оплата получена»/блока 3. После завершения — публикация найденных изменений в GitHub и UI.

Сейчас дополнительно весь сервис временно suspended в Render, поэтому все runtime-процессы остановлены до ручного Resume.

Проект 1-4 (красным): разбить нынешний монолитный цикл refresh (stage1_base → stage2.5 → stage2 → stage3 → stage4 → stage5 → stage6 — единая попытка на весь цикл) на 4 последовательных процесса с промежуточной публикацией после каждого шага: 1/4 = stage1_base+stage2.5+stage2+stage3+stage4+stage5 (карточка КП целиком, кроме заказов/накладных/оплат); 2/4-4/4 = три под-скана, из которых сейчас состоит stage6 (заказы/накладные/оплаты), каждый — отдельным шагом со своей публикацией. Цель — не ускорение сканирования (объем запросов к 1С тот же), а устойчивость к таймауту: если поздний шаг (например, платежи) не укладывается в лимит, уже найденные и опубликованные изменения из более ранних шагов не теряются. Процессы остаются последовательными (не параллельными) — параллелизация трех сканов обсуждалась и была отклонена как более рискованная без доказанной пользы.

От чего зависит длительность полного refresh

  1. Глубина цикла: полный проход дольше, checkpoint-восстановление быстрее.
  2. Скорость 1С OData: чем медленнее ответы, тем дольше общий цикл.
  3. Объем данных (число КП/строк): больше строк = больше запросов и проверок.
  4. Ретраи и таймауты на этапах enrichment (особенно stage2.5/3/4).
  5. Скорость publish в GitHub и подтверждения current-pointer.
  6. Конкуренция за lock: запуск может ждать завершения уже идущего refresh.
  7. Практический диапазон: от десятков секунд до нескольких минут; hard ceiling для manual refresh около 21 минуты.
